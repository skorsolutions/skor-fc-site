# Returning guest picker — v58.32

Implementation complete 2026-11-02 UTC. Frontend production deployment is in progress. Captain v58.31 was the preceding release; Player Portal remains v58.28.

Both the Lineups saved-player selector and Choose Guest dialog include **Reusable guest profiles** and **Saved TEMP names**. Missing RSVP never hides a returning player. The remembered identity pool includes old unused entries; eligibility for match history remains the separate v58.31 rule based on Final/Production field or bench, confirmed Present attendance or official stats/MOTM.

Select a returning name, confirm that the listed saved identities belong to the same person, and choose this game's jersey. Complete saved names are filled automatically. A short historical name asks for the full referee name once. A matching reusable profile is shown once instead of also offering its old saved name as a new person; names are not silently merged or used to bind identities without confirmation.

The reviewed setup uses existing APIs: atomic `manage_guest_history('import')` for eligible historical games or guarded profile creation when no game history is eligible, then explicit identity-only `bind_game` calls for unambiguous unused entries, and `manage_guest_history('assign')` for the selected game. Earlier TEMP IDs, jersey numbers/inventory and active flags remain. A same-game unlinked TEMP is reviewed and bound before assignment, so re-add reuses its original ID. Conflicting identities stop and direct the captain to Roster. Linking unused rows alone does not create match history or mark attendance.

Setup and assignment have separate existing transactions. Successful earlier stages are retained if a later step fails; stable request IDs and payloads allow the same save to finish after a refresh without creating a second profile or match TEMP. A created profile is also available in the normal profile list if the page reloads. Account changes clear pending identities/requests and stop subsequent writes. Snapshot changes are checked before binding an unused identity. Current server safeguards still apply; ambiguous same-name people require explicit Roster review rather than automatic merging.

Match jerseys are independent of the reusable profile and earlier games. Use an available physical inventory item or type the number worn for this match. Permanent guest numbers remain TBD. Only the selected game's existing number is prefilled; a new game's number stays blank. Explicit number-only reassignment can clear the selected game's physical inventory link through the existing guarded API before setting the number. Refresh retains the current in-progress choice, and changing games clears jersey drafts. The editor, exports/referee sheet, Game Day, Strategy and AI consume the same persisted match TEMP identity/number as before.

The picker never writes RSVP or attendance. A separate user-authorized administrative correction created one reusable guest profile, connected two existing eligible match identities and added one current-game assignment with the confirmed jersey and explicitly confirmed Present attendance. It used the existing guarded RPCs under the connected owner's verified captain identity and auditable request IDs. An old removed, unused game assignment remained untouched. Original events, saved lineups, match metadata, RSVP and ledger data fingerprints match baseline; old TEMP IDs and jerseys are retained. No private names, UUIDs or account details are embedded in public documentation or tests.

No SQL migration, schema, grants, RLS or Edge Function changes. The existing database contracts remain unchanged. All 23 local suites and six real-role database rollback suites pass. Tests cover canonical and previous names (including unused identities), one-profile reuse, old/current aliases, separate match jerseys, no inferred RSVP/attendance, exact lost-response retries, partial setup, same-game reuse, duplicate/short-name validation, account isolation and the actual main Lineups handler. Connected keeper/referee/export, optional-number, post-match, guest portal/promotion, attendance and dues regressions pass. All fourteen data fingerprints match the post-repair baseline after the rollback tests. Browser visual review and GitHub commit-comment creation remain unavailable.
